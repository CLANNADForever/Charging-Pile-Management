# Build and dependency rules

Read the relevant Profile module, its `capability_status`, and the repository's actual adapter, build graph and dependency mechanisms before editing build metadata. Do not create a build target, graph entry, export/install/package surface or third-party dependency unless the approved design and Integration inventory allow it. Use reviewed Profile command IDs for configure, build, test, install, package, consumer, static-analysis and target-run capabilities; `absent`, `unavailable`, `not-applicable` or `needs-approval` must be reconciled with the current requirement by Planner, never treated as permission to guess a command. Validate clean configuration when build-graph inputs change. A distribution surface needs a representative downstream configure/build/link and any applicable host or target run, not only a successful main-project build. Inspect broad source collection, install, packaging and CI rules so governance files cannot enter product artifacts.
