

# NCS 充电桩应用管理平台 - 需求与架构规范 (SRS)

## 1. 系统定位与整体架构

本项目是一个模拟真实物理世界的 O2O 共享充电桩管理平台。系统包含用户端的设备查找与计费、运营端的资产管理与控制，以及基于设备运行时数据的 AI 异常检测。

为保证工程的严谨性与扩展性，系统必须采用**前后端物理分离**的架构模式，核心由以下四大独立模块组成：

1. **前端 GUI (Frontend)**：基于 Qt 框架开发的纯 UI 客户端（包含用户端与管理端）。职责仅为界面渲染、用户交互与发送网络请求，**严禁在 UI 层直接连接或操作数据库**。
2. **后端服务 (Backend)**：独立运行的 C++ 服务端程序。负责处理来自客户端的网络请求（如 HTTP/JSON 或 TCP），执行核心业务逻辑（状态机流转、并发控制），并统一对 SQLite 数据库进行持久化操作。
3. **硬件模拟器 (Hardware Simulator)**：独立于主业务逻辑的轻量级模块/脚本，负责在后台模拟充电桩的物理行为（电量随时间增长、随机波动），并向后端上报实时运行数据。
4. **AI 智能模块 (AI Engine)**：独立的 Python/算法脚本。基于无监督学习（如孤立森林）对实时上报的设备数据进行异常检测，或基于合成时序数据进行负荷预测，供后端调用或大屏展示。

## 2. 核心业务需求 (Functional Requirements)

### 2.1 车主用户端 (C端)
* **身份认证**：支持 11 位手机号免密登录。用户输入手机号后，系统本地模拟下发并校验验证码；若手机号不存在则自动完成新用户注册。
* **找站与导航**：
  * **周边查询**：展示附近的充电站列表。每个充电站卡片显示：站名、充电价格（元/度）、电桩总数/空闲数量、距离（公里）；点击充电站可查看该站所有电桩的详细信息（编号、类型、状态、功率）
  * **地图导航**：点击站点可调用外部地图 API（如腾讯地图）生成路线规划，（QWebEngineView加载）；输入起点（当前位置）和终点（目标电站）；点击导航按钮跳转至地图路线规划页面
* **充电与计费闭环 (核心状态机)**：
  * **防并发控制**：进入选桩页面前，必须拦截并校验用户是否有“未结算订单”。
  * **选桩预约**：选择空闲状态的电桩进行预约（需校验余额充足，超时自动释放资源）。
  * **模拟充电**：启动充电后，界面需实时刷新并展示累加的电量、金额与电桩状态。
  * **自动结算**：结束充电时，系统自动释放电桩资源、扣减用户余额，并生成包含明细的订单小票。
* **个人中心**：支持修改个人资料（头像/昵称）、钱包余额查询与模拟充值、历史订单列表查看。

### 2.2 运营管理员端 (B端)
* **权限与审计**：管理员账号认证登录；支持简单的角色权限划分与敏感操作日志审计。
* **资产管理 (站/桩)**：
  * **充电站**：支持建站、修改信息。受外键保护：站内若有绑定电桩，则禁止删除该站。列表展示包括充电站ID、站名、详细地址、经纬度、总电桩数、当前在线率、单价；点击电站，可查看该站所有电桩的实时状态明细
  * **充电桩**：支持批量建桩、检索与筛选。列表展示包括电桩编号、所属电站、类型（快充/慢充）、功率（kW）、当前状态、累计充电次数、累计充电时长，使用中禁删
* **设备监控与控制**：
  * **实时状态**：列表展示电桩的运行状态（空闲/充电中/故障）、功率、电量。
  * **远程干预**：针对故障电桩，可下发“远程重启”指令，模拟设备恢复正常的流转过程。用于处理死机等异常，运维日志
* **用户风控**：支持按手机号搜索用户；可对异常用户进行“冻结/解冻”操作，被冻结账号无法发起新交易。列表展示：用户ID、手机号、昵称、钱包余额、注册时间、状态（正常/冻结）、


### 2.3 经营分析与大屏展示部分（决策者）
* **数据大屏**：提供一个定时刷新的全局视角看板，综合展示核心业务指标（Web端）。
  * **核心指标**：展示今日营收、本月营收、总营收三大核心数字指标；可切换时间维度查看营收变化趋势
  * **图表分析**：使用 Qt Charts 渲染近 7 日/30 日营收趋势折线图，及设备健康度（状态分布）饼图。显示以表格展示当前所有电桩的状态分布：在用、闲置、故障。显示具体数量及占比百分比；直观反映设备整体运行健康度。指标卡、充电量排行、时段分布等


### 2.4 智能预测部分（具体实现待定）
* **智能异常检测**：基于硬件模拟器上报的实时电压/电流/温度等波动数据，运行**无监督学习算法**（如 Isolation Forest），自动识别偏离正常分布的异常电桩，并在管理端产生预警。
* **智能负荷预测**：系统可生成历史合成数据，支持一键训练时序模型，预测未来各站点的空闲桩数与充电负荷，并进行高峰拥堵预警。

## 3. 客户端开发规范 (UI 架构约束)

为适应敏捷开发与后续对接，Qt 客户端代码必须遵循 **MVP/MVC 接口隔离原则**：
1. **数据模型与接口定义 (Model/Service)**：所有业务（如 `IUserService`、`IChargeService`）必须定义为纯虚基类。
2. **纯视图层 (View)**：UI 代码（`.ui` 文件或手写 Widget）只负责数据渲染与事件捕获，不包含任何业务校验与网络操作逻辑。
3. **控制层与依赖注入 (Controller)**：在开发初期，注入 `MockService`（返回假数据）以支撑 UI 开发；后期统一替换为 `HttpService`（或 SocketService）对接真实后端进程。

### 目录结构重构建议

所有的 C++ 代码都在 `src/` 目录下。建议重组 `src/` 目录（仅为参考）：

```
> src/
  ├── CMakeLists.txt            # 顶层 CMake (用于统筹所有子模块)
  │
  ├── common/                   # 公共基础层 (编译为静态库)
  │   ├── CMakeLists.txt        # add_library(common STATIC ...)
  │   ├── entities.h            # 定义所有端共用的结构体 (如 User, Station, Order)
  │   ├── utils/                # 共用的工具类 (如日志、时间格式化)
  │   └── network/              # 共用的基础网络请求封装
  │
  ├── client_user/              # 客户端 1：车主用户端 (C端)
  │   ├── CMakeLists.txt        # add_executable(ncs_user ...), 链接 Qt 和 common
  │   ├── main.cpp              # 强制窗口尺寸为竖屏比例 (如 420x760)
  │   ├── views/                # 车主界面的 UI (地图、扫码、充值)
  │   ├── controllers/
  │   └── services/
  │
  ├── client_admin/             # 客户端 2：运营管理端 (B端)
  │   ├── CMakeLists.txt        # add_executable(ncs_admin ...), 链接 Qt, QtCharts 和 common
  │   ├── main.cpp              # PC 宽屏比例
  │   ├── views/                # 管理界面的 UI (折线图、数据表格、后台菜单)
  │   ├── controllers/
  │   └── services/
  │
  ├── backend_server/           # 服务端：C++ 后端 
  │   ├── CMakeLists.txt        # add_executable(ncs_server ...), 链接 common, SQLite 等
  │   ├── main.cpp              # 启动 HTTP 和 TCP 监听端口
  │   ├── core/                 # 业务逻辑与状态机
  │   └── database/             # SQLite 封装
  │
  ├── simulator/                # 下位机模拟脚本 (Python/C++)
  │
  └── ai_module/                # AI 异常检测与分析脚本
```
